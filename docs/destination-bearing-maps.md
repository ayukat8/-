# 地図で方位を見る 仕様書

奇門遁甲アプリに、**地図で目的地を指定して、それが今日の吉方位かどうかを判定する**機能を追加するための仕様です。
この1枚で完結します。他の仕様書を参照する必要はありません。

参考実装として `map-demo.html` を同梱しています。APIキーなしで動く、この仕様のたたき台です。

---

## 1. この機能の役割

奇門遁甲の方位取りは、**基準点（自宅など）から目的地を見た方角**で判断します。
地図があれば、その方角を計算で出せます。

スマホの方位センサーが使えないユーザー（PC・許可拒否・アプリ内ブラウザ）でも、
**この機能があれば方位取りができます。** 単体で価値のある機能です。

**スコープ外**: 方位磁石そのものの実装、盤の表示。この文書は地図まわりだけを扱います。

---

## 2. 最初に決めてほしいこと

| # | 確認事項 | 選択肢 | 影響 |
|---|---|---|---|
| 1 | 方位の粒度 | 八方位（45°刻み）/ 二十四山（15°刻み） | 扇形の幅、判定の厳しさ |
| 2 | 地図サービス | §6の表から選ぶ | 費用・APIキー管理・利用規約 |
| 3 | 対応範囲 | 国内のみ / 海外も | 海外を含むなら §3 の注記表示とタイルの手当が必要 |
| 4 | 距離の下限 | 閾値を設けるか | 「基準点から1km未満は判定しない」等 |

**方位の計算方法は決定済みです**（§3）。地図上の直線を採用し、大圏コースは実装しません。

## 3. 方位の計算

### 決定事項: 地図上の直線（等角航路）を使う

方位角の定義には2通りあり、遠方では結果が大きく異なります。

- **大圏コース**: 地球上の最短経路。飛行機が飛ぶ方角。**採用しません。**
- **地図上の直線（等角航路）**: メルカトル図法の地図に定規を当てて引いた線の角度。**こちらを採用します。**

東京駅を基準点として実際に計算した比較です。

| 目的地 | 距離km | 大圏 | 地図上 | 差 | 八方位（大圏 / 地図上） |
|---|---:|---:|---:|---:|---|
| 横浜駅 | 27 | 208.7° | 208.7° | 0.0° | 南西 / 南西 |
| 大阪駅 | 403 | 255.6° | 254.3° | 1.2° | 西 / 西 |
| 札幌 | 832 | 8.9° | 9.4° | 0.5° | 北 / 北 |
| ソウル | 1,159 | 284.2° | 280.4° | 3.8° | 西 / 西 |
| 那覇 | 1,559 | 230.9° | 227.5° | 3.3° | 南西 / 南西 |
| シドニー | 7,825 | 169.9° | 171.2° | 1.3° | 南 / 南 |
| **ホノルル** | 6,199 | 87.0° | 104.8° | **17.7°** | 東 / 東（二十四山では別の山） |
| **ロサンゼルス** | 8,810 | 55.6° | 91.1° | **35.5°** | **北東 / 東** |
| **パリ** | 9,716 | 333.5° | 277.4° | **56.1°** | **北西 / 西** |

**国内は差が3.8°以内**で、八方位でも二十四山でも判定は一致します。
**海外は割れます。** 東京からパリは、大圏なら北西、地図上なら西。吉方位が凶方位に変わる規模の差です。

地図に定規を当てた線と判定が一致するほうがユーザーには納得しやすいため、地図上の直線を採用します。
ただし飛行機の方角とは異なるので、**遠距離（例: 2,000km以上）では「地図上の直線で計算しています」と一言添えてください。**
併記や切り替えは不要です。

### 実装

```js
const toRad = d => d * Math.PI / 180;
const toDeg = r => r * 180 / Math.PI;

/** 地図（メルカトル図法）上で直線に見える方位角＝等角航路。真北基準・時計回り・0〜360 */
export function rhumbBearing(lat1, lng1, lat2, lng2) {
  const φ1 = toRad(lat1), φ2 = toRad(lat2);
  let Δλ = toRad(lng2 - lng1);
  if (Math.abs(Δλ) > Math.PI) Δλ -= Math.sign(Δλ) * 2 * Math.PI;  // 日付変更線をまたぐ場合
  const Δψ = Math.log(Math.tan(Math.PI / 4 + φ2 / 2) / Math.tan(Math.PI / 4 + φ1 / 2));
  return (toDeg(Math.atan2(Δλ, Δψ)) + 360) % 360;
}

/** 2点間の距離（km） */
export function distanceKm(lat1, lng1, lat2, lng2) {
  const φ1 = toRad(lat1), φ2 = toRad(lat2);
  const Δφ = φ2 - φ1, Δλ = toRad(lng2 - lng1);
  const a = Math.sin(Δφ / 2) ** 2 + Math.cos(φ1) * Math.cos(φ2) * Math.sin(Δλ / 2) ** 2;
  return 6371 * 2 * Math.asin(Math.sqrt(a));
}
```

**返る値は常に真北基準です。** 地図由来の方位に磁気偏角の問題は関係しません
（方位センサーを使う場合のみ、磁北との差が問題になります）。

## 4. 奇門遁甲側から受け取るデータ

既存の奇門遁甲ロジックを、次の形で公開してください。**これが唯一の結合点**です。

```ts
type Verdict = "auspicious" | "inauspicious" | "neutral";

interface DirectionVerdict {
  bearing: number;   // セクター中心の方位角。真北基準・時計回り・0〜359.99
                     // 例) 北=0, 東=90, 南=180, 西=270, 東南=135
  span: number;      // セクターの幅（度）。八方位=45、二十四山=15
  name: string;      // 表示名。"東南" / "巽" など
  verdict: Verdict;
  title?: string;    // 格・門の名称。"生門" など（既存ロジックの値をそのまま）
  note?: string;     // 一言説明。30字程度
}

interface EventSectors {
  eventId: string;    // "study" | "love" | "money" | ...
  eventName: string;  // "勉強・試験"
  directions: DirectionVerdict[];
  validFrom: string;  // ISO8601
  validTo: string;    // ISO8601。日家なら当日の終わり、時家なら2時間後
}

/** 指定時刻・指定イベントの吉凶方位を返す */
function getSectors(at: Date, eventId: string): EventSectors;
```

### 約束事

- `bearing` は**必ず真北基準**にしてください（磁北ではありません）。
- 中宮（方位なし）は `directions` に含めないでください。方位として表示できません。
- セクターが重ならないこと。同一 `bearing` に複数の判定を返さないこと。
- 吉方位が0件の日もあり得ます。その場合も画面が壊れないようにしてください。

### 判定

```js
function angleDiff(a, b) { return Math.abs(((a - b + 540) % 360) - 180); }

/** 方位角が入るセクターを返す。該当なしは null */
function sectorFor(bearing, sectors) {
  return sectors.find(s => angleDiff(bearing, s.bearing) <= s.span / 2) || null;
}

/** セクター境界から±5°以内か */
function nearBoundary(bearing, sectors) {
  const s = sectorFor(bearing, sectors);
  return s ? Math.abs(angleDiff(bearing, s.bearing) - s.span / 2) <= 5 : false;
}
```

```ts
interface BearingResult {
  bearing: number;                   // 方位角（真北基準・地図上の直線）
  distanceKm: number;
  sector: DirectionVerdict | null;   // 該当セクター。範囲外なら null
  boundaryWarning: boolean;          // 境界から±5°以内なら true
}
```

## 5. 基準点と目的地の指定

- **基準点と目的地は、どちらも同じUIで任意に指定できること。** 基準点を自宅に固定しないでください。
  旅先から次の目的地を見る、友人の家を基準にするなど、その場で基準点を変えたい場面があります。
- **入れ替えボタン**を置いてください（往路と復路の確認に使えます）。
- 指定方法は5つ用意してください。1つでも欠けると詰むユーザーが出ます。

| 方法 | 用途 | APIの要否 |
|---|---|---|
| 場所の検索 | 主たる入力手段 | 検索API（§6） |
| 現在地から取得 | 今いる場所を基準点にする | 不要（Geolocation） |
| 地図をタップ | 検索で出ない場所、大まかな指定 | 不要（§7） |
| 緯度経度の直接入力 | 座標が分かっている場合 | 不要 |
| 地図アプリの共有URLを貼り付け | 他アプリで見つけた場所 | 不要（§7） |

- 直近に使った基準点は `localStorage` に保存し、次回の初期値にしてください（固定ではなく既定値として）。

```ts
interface Place {
  label: string;   // "京都駅" — ユーザーに見せる名前
  lat: number;
  lng: number;
  source: "search" | "current-location" | "map-tap" | "manual" | "url";
}
```

## 6. 地図サービスの選択肢

### 前提: リンクを開くだけの連携では判定できません

`https://www.google.com/maps/search/?api=1&query=...` のようなURLでGoogleマップを開くことはできますが、
**ユーザーが向こうで選んだ場所の座標はアプリに返ってきません。** 一方通行です。
判定するには、**アプリ内で座標を取得する**必要があります。

### 検索（ジオコーディング）

| 案 | 検索の網羅性 | 費用 | 主な制約 |
|---|---|---|---|
| **1. Google Places Autocomplete** | 最良。店名・施設名・通称まで拾える | 従量課金 | APIキー必須。キー漏洩＝請求事故 |
| **2. Mapbox / MapTiler の Geocoding** | 良好。日本の住所も実用的 | 無料枠あり＋従量 | APIキー必須 |
| **3. Photon（OSMベース）** | 中。店名は弱いが地名・住所は拾える | 無料 | 公開インスタンスは fair-use。自前ホストも可 |
| **4. Nominatim（OSM）** | 中。日本の住所はやや弱い | 無料 | **1リクエスト/秒。入力補完は利用規約で禁止** |
| **5. 国土地理院の住所検索** | 国内の住所・地名は良好。施設名は弱い | 無料 | 国内のみ。出典表示。仕様が公開文書化されていない |
| **6. 自前データを同梱** | 用意した範囲のみ | 無料 | 国土地理院「位置参照情報」等でオフライン検索も可能 |

**入力補完（打つたびに候補を出す）をやりたいなら、案4は使えません。** Nominatimの利用規約が
autocomplete用途を禁じています。作り込んでから気づくと手戻りになります。

**推奨は案1**ですが、課金を避けたいなら案3や案6でも機能は成立します。
方位計算は地図サービスに依存しないため、**後から乗り換え可能**です。
`searchPlace(query) → { label, lat, lng }` で抽象化しておいてください。

利用条件・無料枠・規約はいずれも変更されます。**実装前に各サービスの最新の条件を確認してください。**

### Google Maps Platform を使う場合

- **APIキーには必ずHTTPリファラ制限をかける。** 無制限のキーが漏れると請求が発生します。
- **予算アラートを設定する。** 想定外のループやボットで課金が跳ねる事故を防げます。
- **無料枠の条件は2025年に変更されています。** 実装前に最新の料金ページで確認してください。
- **Autocomplete はセッション単位で課金されます。** セッショントークンを正しく使わないと、1文字ごとに課金され得ます。
- **取得したPlaceデータの長期保存には制限があります**（`place_id` は保存可、他は一時キャッシュのみ）。

### 地図の表示（タイル）

検索とは**別のサービス**であり、別に課金されます。

| | 無料の道 | 注意 |
|---|---|---|
| 国内 | 地理院タイル | 出典表示が必須。日本国内のみ |
| 海外を含む | 自前ホストのOSMタイル、MapTiler等の無料枠 | 公開OSMタイルサーバの直接利用はアプリ用途に向きません |

**Google Maps JavaScript API は地図の表示自体が課金対象です。** 完全に無料にしたいなら
**Leaflet + 地理院タイル（国内）**の組み合わせにしてください（`map-demo.html` がこの構成です）。

## 7. APIを使わずに座標を得る道（必ず併用してください）

検索でどうしても出ない場所は必ずあります。以下2つは通信もAPIキーも不要です。

### 7-1. 地図アプリの共有URLを貼り付けてもらう

Googleマップやアップルマップで場所を開き、URLをコピーして貼るだけ。

```js
// !3d/!4d が場所の実座標。@ は地図の中心なので優先度は下
const PATTERNS = [
  /!3d(-?\d+\.\d+)!4d(-?\d+\.\d+)/,
  /\/@(-?\d+\.\d+),(-?\d+\.\d+)/,
  /[?&](?:q|query|ll|daddr|center)=(-?\d+\.\d+),\s*(-?\d+\.\d+)/,
  /^geo:(-?\d+\.\d+),(-?\d+\.\d+)/
];
```

**注意**: スマホの共有ボタンから出てくる短縮URL（`maps.app.goo.gl/...`）には座標が入っていません。
展開にはリダイレクトを辿る必要があり、ブラウザからはCORSで弾かれます。
サーバ側に小さな展開エンドポイントを置くか、「地図アプリで開いてからURLをコピーしてください」と案内してください。

### 7-2. 地図をタップして選んでもらう

**地図ライブラリは画面上の全ピクセルの緯度経度をすでに知っています。**
タップ地点の座標は内部の計算だけで得られ、通信は発生しません。

```js
// Leaflet の場合。これだけで座標が取れる
map.on("click", e => {
  setDestination({ label: "地図で選んだ地点", lat: e.latlng.lat, lng: e.latlng.lng });
});
```

**地名に変換する必要はありません。** 判定に要るのは座標だけです。
タップ地点を「◯◯駅」と表示するには逆ジオコーディング（これもAPI）が必要になるので、
`地図で選んだ地点` のままにすればAPIはゼロで済みます。

**限界**: タップは「だいたいこのへん」には向きますが、「京都駅」を指すには地図を探させることになります。
**検索の置き換えではなく併用**が現実的です。

### 8-1. 判定画面

```

├────────────────────────────┤
│ 基準点  [ 東京駅            ]🔍 │

│         西南西 ・ 258.0°         │

│    ◎ 今日の吉方位です            │
│      西 — 生門・学びに追い風       │
├────────────────────────────┤
│ [ 地図で見る ]                   │
└────────────────────────────┘
```

- 吉＝金色、凶＝灰色、範囲外＝無彩色。アプリの他の画面と**同じ配色**を使ってください
- `boundaryWarning` が立っていたら「境界に近い方角です」と添える
- 遠距離（例: 2,000km以上）では「地図上の直線で計算しています」と注記（§3）
- 距離が閾値未満なら「近すぎるため方位取りの対象外です」と表示
- イベントを切り替えるチップを置き、同じ2地点のまま判定を切り替えられるようにする

### 8-2. 地図画面

- 基準点を中心に、吉方位セクターを金色（`#c9964a` / `opacity: 0.28`）、
  凶方位を灰色（`#a89ba1` / `opacity: 0.15`）の扇形で描画
- 扇の半径は既定 400km 相当。ズームに応じて画面外まで伸ばす
- 目的地ピンを立て、基準点との間に線を引く
- 基準点・目的地のピンはドラッグで動かせる
- **地図をタップした地点の方位も即座に判定**する

**扇形は投影後の座標で作ってください。** メルカトル図法上でまっすぐな扇形になり、
判定（地図上の直線）と見た目が一致します。大圏コース用の弧を描く実装と混ぜると、
「地図では吉方位の扇に入っているのに判定は凶」という矛盾が起きます。

```js
// map-demo.html より。REF_ZOOM は任意の固定ズーム
const p0 = map.project(origin, REF_ZOOM);
const scale = (256 * Math.pow(2, REF_ZOOM)) / (40075016.686 * Math.cos(toRad(origin.lat)));
const r = SECTOR_RADIUS_M * scale;
for (let a = a1; a <= a2; a += 5) {
  const t = toRad(a);
  pts.push(map.unproject(L.point(p0.x + r * Math.sin(t), p0.y - r * Math.cos(t)), REF_ZOOM));
}
```

## 9. プライバシー

- **基準点の座標は端末内に保存し、サーバに送らないでください。** 自宅位置は機微な情報です。
- 現在地の取得は、何に使うかを説明してから許可を求めてください（「基準点の設定に使います」）。
- 位置情報を拒否されても使えるようにしてください。**必須にしないこと。**
- 検索クエリを外部APIに送る以上、目的地は第三者サービスに渡ります。プライバシーポリシーに明記してください。

## 11. 受け入れ基準

- [ ] 東京駅→大阪駅で 254.3°、「西」と判定される
- [ ] 東京駅→パリで 277.4°、「西」と判定される（大圏の 333.5°／北西 にはならないこと）
- [ ] 日付変更線をまたぐ目的地（東京→ホノルル 104.8°）で方位が破綻しない
- [ ] 往路と復路で方位が正しく反転する（東京→ホノルル 104.8° ⇔ ホノルル→東京 284.8°）
- [ ] **基準点を自由に変更でき、目的地と入れ替えられる**
- [ ] 検索・現在地・地図タップ・座標入力・URL貼り付けの5経路すべてで座標を設定できる
- [ ] 短縮URLを貼られたときに案内が出る
- [ ] 位置情報を拒否しても機能が使える
- [ ] 地図上の扇形と、テキストの判定結果が矛盾しない
- [ ] セクター境界±5°で「境界に近い」警告が出る
- [ ] 基準点と目的地が同一・極端に近い場合にエラーにならない
- [ ] 吉方位が0件の日でも画面が壊れない
- [ ] 時家の場合、時辰をまたいだ時点で判定が自動更新される
- [ ] APIキーにリファラ制限がかかっている（コードレビュー項目）

## 付録: そのまま渡す指示文

> 奇門遁甲アプリに「地図で目的地の方位を見る」機能を追加してください。仕様は `docs/destination-bearing-maps.md`、
> 参考実装は `map-demo.html` です。
>
> 1. 基準点と目的地を指定し、その2点間の方位角を計算して、その日のイベントの吉凶方位と照合して判定を表示すること。
> 2. **方位角は「地図上の直線（等角航路）」で計算すること。大圏コースは実装しない。**
>    国内では両者の差は3.8°以内だが、東京→パリでは大圏333.5°（北西）に対し地図上277.4°（西）と56°食い違う。
>    採用するのは後者。遠距離では「地図上の直線で計算しています」と注記を出すこと。
> 3. **基準点と目的地は、どちらも同じUIで任意に指定でき、入れ替えられること**（基準点を自宅に固定しない）。
>    指定方法は5つ用意すること: 検索 / 現在地 / 地図タップ / 緯度経度の直接入力 / 地図アプリの共有URL貼り付け。
> 4. Googleマップを外部リンクで開く方式では座標が返ってこないため、判定には使えない。アプリ内で座標を取得すること。
> 5. 地図サービスは差し替え可能なように `searchPlace(query) → { label, lat, lng }` で抽象化すること。
>    Google Maps Platform を使う場合、APIキーにHTTPリファラ制限をかけ、予算アラートを設定すること。
>    入力補完を実装する場合、Nominatimは規約上使えないので注意すること。
> 6. 地図に扇形を描く場合、投影後の座標で直線的な扇形を描くこと（判定と描画を一致させる）。
> 7. **基準点の座標は端末内に保存し、サーバに送らないこと。** 位置情報の許可は必須にしないこと。
> 8. 奇門遁甲側からは `getSectors(at: Date, eventId: string): EventSectors` で吉凶方位を受け取ること（型は §4）。
>    `bearing` は真北基準で返すこと。
> 9. 受け入れ基準は §11 のチェックリスト。特に東京→大阪（254.3°／西）と東京→パリ（277.4°／西）を確認すること。
>
> 着手前に、§2 の4点（方位の粒度／地図サービス／対応範囲／距離の下限）を確定して回答してください。
