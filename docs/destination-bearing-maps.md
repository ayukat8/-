# 目的地の方位判定（地図連携）仕様書

「行きたい場所を指定すると、それが今日の吉方位かどうかを判定する」機能の仕様です。
統合仕様書 `qimen-compass-integration.md` の §6（案B）を具体化したものです。

コンパスは「いま端末がどちらを向いているか」しか測れませんが、地図と組み合わせると
**基準点（自宅）から目的地を見た方角**が計算でき、方位取り本来の使い方ができるようになります。

## 1. できること（機能一覧）

| 機能 | 内容 | 優先度 |
|---|---|---|
| **A. 目的地の方位判定** | 場所名・住所を入力 → 基準点からの方位角を計算 → 吉凶を判定 | 必須 |
| **B. 地図に吉方位を重ねる** | 基準点を中心に、吉方位セクターを金色の扇形で地図上に描画 | 高 |
| **C. コンパスとの連動** | 文字盤に目的地マーカーを出し、その方角を向くと「目的地はこちら」 | 中 |
| **D. 吉方位から探す（逆引き）** | 「今日の吉方位にあるカフェ」を検索 | 低（面白いが後回し可） |

Aだけでも「コンパスが使えない人が方位取りできる」という価値が出ます。**盤モードのユーザーにも効く機能**です。

## 2. 方位の計算方法（決定済み: 地図上の直線）

同じ2地点でも、**方位角の定義が2通りあり、遠方では結果が大きく異なります。**

- **大圏コース（初期方位）**: 地球上の最短経路。出発時に実際に向く方角。飛行機が飛ぶ経路。
- **地図上の直線（等角航路）**: メルカトル図法の地図に定規を当てて引いた線の角度。

東京駅を基準点として実際に計算した結果です。

| 目的地 | 距離km | 大圏 | 地図上 | 差 | 八方位（大圏 / 地図上） |
|---|---:|---:|---:|---:|---|
| 横浜駅 | 27 | 208.7° | 208.7° | 0.0° | 南西 / 南西 |
| 大阪駅 | 403 | 255.6° | 254.3° | 1.2° | 西 / 西 |
| 札幌 | 832 | 8.9° | 9.4° | 0.5° | 北 / 北 |
| ソウル | 1,159 | 284.2° | 280.4° | 3.8° | 西 / 西 |
| 那覇 | 1,559 | 230.9° | 227.5° | 3.3° | 南西 / 南西 |
| シドニー | 7,825 | 169.9° | 171.2° | 1.3° | 南 / 南 |
| **ホノルル** | 6,199 | 87.0° | 104.8° | **17.7°** | 東 / 東（二十四山では別の山） |
| **ロサンゼルス** | 8,810 | 55.6° | 91.1° | **35.5°** | **北東 / 東** |
| **パリ** | 9,716 | 333.5° | 277.4° | **56.1°** | **北西 / 西** |

### 読み取れること

- **国内は差が3.8°以内**で、八方位でも二十四山でも判定は一致します。**国内のみの対応なら、どちらを選んでも同じ結果**になります。
- **海外は判定が割れます。** 東京からパリは、大圏なら北西、地図上なら西。**吉方位が凶方位に変わる規模の差**です。

### 採用する定義: 地図上の直線（等角航路）

**このアプリは「地図上の直線」で方位を判定します。大圏コースは採用しません。**

地図に定規を当てて引いた線の角度と判定が一致するため、ユーザーが地図を見て納得できる挙動になります。
国内では大圏コースとの差は3.8°以内で、どちらでも判定は変わりません。

海外の目的地では両者が大きく食い違うため、**距離が長い場合（例: 2,000km以上）は
「地図上の直線で計算しています」と一言添えてください。** 飛行機の飛ぶ方角（大圏コース）とは
異なるため、それを期待したユーザーへの説明になります。併記や切り替えは不要です。

### 実装

```js
const toRad = d => d * Math.PI / 180;
const toDeg = r => r * 180 / Math.PI;

/** 地図（メルカトル図法）上で直線に見える方位角＝等角航路。真北基準・時計回り・0〜360 */
export function rhumbBearing(lat1, lng1, lat2, lng2) {
  const φ1 = toRad(lat1), φ2 = toRad(lat2);
  let Δλ = toRad(lng2 - lng1);
  if (Math.abs(Δλ) > Math.PI) Δλ -= Math.sign(Δλ) * 2 * Math.PI;  // 日付変更線をまたぐ場合
  const Δψ = Math.log(Math.tan(Math.PI / 4 + φ2 / 2) / Math.tan(Math.PI / 4 + φ1 / 2));
  return (toDeg(Math.atan2(Δλ, Δψ)) + 360) % 360;
}

/** 2点間の距離（km） */
export function distanceKm(lat1, lng1, lat2, lng2) {
  const φ1 = toRad(lat1), φ2 = toRad(lat2);
  const Δφ = φ2 - φ1, Δλ = toRad(lng2 - lng1);
  const a = Math.sin(Δφ / 2) ** 2 + Math.cos(φ1) * Math.cos(φ2) * Math.sin(Δλ / 2) ** 2;
  return 6371 * 2 * Math.asin(Math.sqrt(a));
}
```

**真北基準**で返ります。奇門遁甲側の `bearing`（真北基準）とそのまま比較できます。
コンパスの磁北問題（統合仕様書 §5）は、この計算には一切関係しません。地図由来の方位は常に真北です。

### 描画との整合

地図に扇形を描くとき（機能B）は、**投影後の座標で直線的な扇形**を描いてください。
地図上でまっすぐな扇形に見え、判定（地図上の直線）と一致します。

大圏コース用の弧を描く実装（`computeOffset()` を使うもの）と混ぜないでください。
ずれると「地図では吉方位の扇に入っているのに、判定は凶」という矛盾が起きます。

## 3. 地図サービスの選択肢

### 重要な前提: リンクを開くだけの連携では判定できません

`https://www.google.com/maps/search/?api=1&query=...` のようなURLでGoogleマップを開くことはできますが、
**ユーザーが向こうで選んだ場所の座標はアプリに返ってきません。** 一方通行です。
方位を判定するには、**アプリ内で目的地の緯度経度を取得する**必要があります。

| 案 | 検索の網羅性 | 費用 | 主な制約 |
|---|---|---|---|
| **1. Google Places Autocomplete** | 最良。店名・施設名・通称まで拾える | 従量課金 | APIキー必須。キー漏洩＝請求事故 |
| **2. Mapbox / MapTiler の Geocoding** | 良好。日本の住所も実用的 | 無料枠あり＋従量 | APIキー必須 |
| **3. Photon（OSMベース）** | 中。店名は弱いが地名・住所は拾える | 無料 | 公開インスタンスは fair-use。自前ホストも可 |
| **4. Nominatim（OSM）** | 中。日本の住所はやや弱い | 無料 | **1リクエスト/秒。入力補完（1文字ごとの検索）は利用規約で禁止** |
| **5. 国土地理院の住所検索** | 国内の住所・地名は良好。施設名は弱い | 無料 | 国内のみ。出典表示。仕様が公開文書化されていない点に注意 |
| **6. 自前データを同梱** | 用意した範囲のみ | 無料 | 国土地理院「位置参照情報」等を同梱すればオフライン検索も可能 |

**入力補完（打つたびに候補を出す）をやりたいなら、案4は使えません。** Nominatimの利用規約が
autocomplete用途を禁じているためです。補完が要るなら案1・2・3、または案6のローカル検索にしてください。

**推奨は案1**ですが、課金を避けたいなら案3または案6でも機能は成立します。
方位計算（§2）は地図サービスに依存しないため、**後から乗り換え可能**です。
`searchPlace(query) → {name, lat, lng}` というインターフェースで抽象化しておいてください。

利用条件・無料枠・規約はいずれも変更されます。**実装前に各サービスの最新の条件を確認してください。**

### APIを使わずに座標を得る道（併用推奨）

検索APIのコストや制限を避けたい場合、**ユーザーに座標を持ってきてもらう**手もあります。
どちらも通信不要で、APIキーもかかりません。**メインの検索と併用すると、取りこぼしが減ります。**

1. **地図アプリの共有URLを貼り付けてもらう**
   Googleマップやアップルマップで場所を開き、URLをコピーして貼るだけ。URLに座標が含まれていれば取り出せます。

   ```js
   // !3d/!4d が場所の実座標。@ は地図の中心なので優先度は下
   const PATTERNS = [
     /!3d(-?\d+\.\d+)!4d(-?\d+\.\d+)/,
     /\/@(-?\d+\.\d+),(-?\d+\.\d+)/,
     /[?&](?:q|query|ll|daddr|center)=(-?\d+\.\d+),\s*(-?\d+\.\d+)/,
     /^geo:(-?\d+\.\d+),(-?\d+\.\d+)/
   ];
   ```

   **注意**: スマホの共有ボタンから出てくる短縮URL（`maps.app.goo.gl/...`）には座標が入っていません。
   展開するにはリダイレクトを辿る必要があり、ブラウザからはCORSで弾かれます。
   サーバ側に小さな展開エンドポイントを置くか、「地図アプリで開いてからURLをコピーしてください」と案内してください。

2. **地図をタップして選んでもらう**

   ここで前提を分けて考えてください。地図まわりのサービスは、**性質の違う2つ**が混ざっています。

   | | 何をするもの | 課金の型 | 無料の道 |
   |---|---|---|---|
   | **地図の表示**（タイル） | 地図の画像を配信する | 表示回数・タイル数 | 地理院タイル（国内・出典表示）、自前ホストのOSMタイル |
   | **住所検索**（ジオコーディング） | 「京都駅」→ 緯度経度 に変換する | リクエスト数 | §3の表を参照 |

   **タップで不要になるのは後者だけです。** 地図を出すこと自体は別途必要です。

   なぜ検索が要らないかというと、**地図ライブラリは画面上の全ピクセルの緯度経度をすでに知っている**からです。
   タップ地点の座標はライブラリ内部の計算だけで得られ、通信は発生しません。

   ```js
   // Leaflet の場合。これだけで座標が取れる
   map.on("click", e => {
     setDestination({ label: "地図で選んだ地点", lat: e.latlng.lat, lng: e.latlng.lng });
   });
   ```

   **地名に変換する必要はありません。** 方位の計算に要るのは緯度経度だけです。
   タップ地点を「◯◯駅」と表示したくなりますが、それには逆ジオコーディング（これもAPI）が必要になります。
   `地図で選んだ地点` のような表示のままにすれば、APIはゼロで済みます。

   **動く実装サンプルがあります**: リポジトリ直下の `map-demo.html` が、この章の内容
   （Leaflet + 地理院淡色タイル、タップで座標取得、投影後の座標で描く扇形、等角航路での判定）を
   1ファイルで実装したものです。APIキーはありません。そのまま出発点にできます。

   **費用の組み合わせに注意**: Google Maps JavaScript API は**地図の表示自体が課金対象**です。
   Googleの地図の上でタップさせても課金は発生します。完全に無料にしたいなら
   **Leaflet + 地理院タイル（国内）または自前ホストのOSMタイル**の組み合わせにしてください。

   **UXの限界**: タップは「だいたいこのへん」を指すには向きますが、「京都駅」を指すには
   地図をスクロールして探させることになります。**検索の置き換えではなく併用**が現実的です。
   検索で見つからなかったときの逃げ道、地図を見ながら「この方角に何がある？」を試す用途に効きます。

### Google Maps Platform を使う場合の注意

- **APIキーは必ず制限をかける。** フロントエンドに置くキーはHTTPリファラ制限を必須にしてください。無制限のキーが漏れると請求が発生します。
- **予算アラートを設定する。** 想定外のループやボットで課金が跳ねる事故を防げます。
- **無料枠の条件は2025年に変更されています。** 実装前に最新の料金ページで確認してください。
- **Autocomplete はセッション単位で課金されます。** セッショントークンを正しく使わないと、1文字ごとに課金される可能性があります。
- **利用規約上、取得したPlaceデータの長期保存には制限があります**（`place_id` は保存可、他のフィールドは一時キャッシュのみ）。
  「よく行く場所」を保存する機能を作る場合は、`place_id` と自前の表示名・座標の扱いを規約で確認してください。

## 4. データ契約の追加

統合仕様書 §3 の型に、以下を追加します。

```ts
interface Place {
  label: string;        // "京都駅" — ユーザーに見せる名前
  lat: number;
  lng: number;
  placeId?: string;     // Google Places の place_id（保存する場合）
  source: "search" | "current-location" | "manual";
}

interface BearingResult {
  bearing: number;          // 方位角（真北基準・地図上の直線）
  distanceKm: number;
  sector: DirectionVerdict | null;   // 該当セクター。範囲外なら null
  boundaryWarning: boolean; // セクター境界から±5°以内なら true
}

/** 基準点から目的地への方位を判定する */
function judgeDestination(origin: Place, destination: Place, advice: EventAdvice): BearingResult;
```

**基準点・目的地の扱い**

- **基準点と目的地は、どちらも同じ検索UIで任意に指定できること。** 基準点を自宅に固定しないでください。
  旅先から次の目的地を見る、友人の家を基準にするなど、その場で base を変えたい場面があります。
- 指定方法は5つ: 場所の検索 / 現在地から取得 / 地図をタップ / 緯度経度の直接入力 / 地図アプリの共有URLを貼り付け
- **基準点と目的地を入れ替えるボタン**を置いてください（往路と復路の確認に使えます）
- 直近に使った基準点は `localStorage` に保存し、次回の初期値にする（固定ではなく既定値として）
- 統合仕様書の `Advice.origin` は、この「現在選ばれている基準点」を指します

## 5. 画面仕様

### 5-1. 目的地の判定画面

```
┌────────────────────────────┐
│ 🧳 旅行・おでかけ    〜15:00 まで │
├────────────────────────────┤
│ 基準点  [ 東京駅            ]🔍 │
│              ⇅ 入れ替える        │
│ 目的地  [ 京都駅            ]🔍 │
├────────────────────────────┤
│         西南西 ・ 258.0°         │
│      基準点から 372km            │
│                                │
│    ◎ 今日の吉方位です            │
│      西 — 生門・学びに追い風       │
├────────────────────────────┤
│ [ 地図で見る ]  [ コンパスで確認 ] │
└────────────────────────────┘
```

- 判定結果は、吉＝金色、凶＝灰色、範囲外＝無彩色で、コンパス・盤モードと**同じ配色**を使う
- `boundaryWarning` が立っていたら「境界に近い方角です」と添える
- 遠距離（例: 2,000km以上）では「地図上の直線で計算しています」と注記を表示（§2）
- 距離が閾値（例: 1km）未満なら「近すぎるため方位取りの対象外です」と表示

### 5-2. 地図表示（機能B）

- 基準点を中心に、吉方位セクターを金色（`#dbb26a` / `opacity: 0.3`）、凶方位を灰色（`opacity: 0.15`）の扇形で描画
- 扇の半径は既定 50km。地図のズームに応じて画面端まで伸ばす
- 目的地ピンを立て、基準点との間に線を引く
- 扇形の描画方法は §2 の「描画との整合」に従う
- 地図はドラッグで自由に動かせ、**地図をタップした地点の方位も即座に判定**できると使い勝手が良い
  （タップ地点の座標は地図ライブラリから直接得られ、検索APIも逆ジオコーディングも不要です）

### 5-3. コンパスとの連動（機能C）

- 目的地を設定すると、コンパスの文字盤に**目的地マーカー**（📍）が方位角の位置に立つ
- 端末をその方角に向けると「京都駅はこちら（西南西）」と表示
- これで「地図で決めた目的地」と「実際に体を向ける方角」が繋がります

### 5-4. 吉方位から探す（機能D・後回し可）

1. 吉方位セクターの中心方向に、基準点から一定距離（例: 5km）進んだ点を求める
2. その点を中心に半径2km程度で周辺検索（カフェ・神社など）
3. **取得結果を方位角で再フィルタ**して、セクターの外に出た候補を捨てる

周辺検索APIは円形しか指定できないため、扇形での絞り込みは自前のフィルタが必要です。

## 6. プライバシー

- **基準点（自宅の座標）は端末内に保存し、サーバに送らないでください。** 自宅位置は機微な情報です。
- 現在地の取得は、何に使うかを説明してから許可を求めてください（「基準点の設定に使います」）。
- 位置情報を拒否されても、住所検索と地図タップで基準点を設定できるようにしてください。**必須にしない**こと。
- 検索クエリを外部APIに送る以上、目的地は第三者サービスに渡ります。プライバシーポリシーに明記してください。

## 7. 受け入れ基準

- [ ] 東京駅→大阪駅で 254.3°、「西」と判定される
- [ ] 東京駅→パリで 277.4°、「西」と判定される（大圏の 333.5°／北西 にはならないこと）
- [ ] 日付変更線をまたぐ目的地（例: 東京→ホノルル 104.8°）で方位が破綻しない
- [ ] 往路と復路で方位が正しく反転する（東京→ホノルル 104.8° ⇔ ホノルル→東京 284.8°）
- [ ] **基準点を自由に変更でき、目的地と入れ替えられる**
- [ ] 基準点が未設定のとき、設定を促す導線が出る
- [ ] 位置情報を拒否しても、場所の検索や緯度経度の直接入力で基準点を設定できる
- [ ] 地図アプリの共有URLを貼り付けて座標を取り出せる（短縮URLの場合は案内を出す）
- [ ] 検索で目的の場所が出ないとき、代替手段（座標入力・URL貼り付け・地図タップ）に導ける
- [ ] 地図上の扇形と、テキストの判定結果が矛盾しない（§2の描画整合）
- [ ] セクター境界±5°で「境界に近い」警告が出る
- [ ] 基準点と目的地が同一・極端に近い場合にエラーにならない
- [ ] オフライン時、地図は出ないが**保存済みの基準点と手入力の座標では判定できる**
- [ ] APIキーにリファラ制限がかかっている（コードレビュー項目）

## 付録: Codex にそのまま渡す指示文

> 奇門遁甲アプリに「目的地の方位判定」機能を追加してください。仕様は `docs/destination-bearing-maps.md` の通りです。
>
> 1. **基準点と目的地を、どちらも同じ検索UIで任意に指定できるようにすること**（基準点を自宅に固定しない）。
>    入れ替えボタンも用意すること。その2点間の方位角を計算し、その日のイベントの吉凶方位と照合して判定を表示すること。
> 2. **方位角は「地図上の直線（等角航路）」で計算すること。大圏コースは実装しない。**
>    国内では両者の差は3.8°以内だが、東京→パリでは大圏333.5°（北西）に対し地図上277.4°（西）と56°食い違う。
>    採用するのは後者。遠距離では「地図上の直線で計算しています」と注記を出すこと。
> 3. 地図サービスは差し替え可能なように `searchPlace(query) → {name, lat, lng}` で抽象化すること。
>    Google Maps Platform を使う場合、APIキーには必ずHTTPリファラ制限をかけ、予算アラートを設定すること。
>    入力補完を実装する場合、Nominatimは規約上使えないので注意すること。
> 3b. 検索APIに加えて、**地図アプリの共有URLの貼り付け**と**緯度経度の直接入力**を必ず用意すること。
>    検索で出ない場所の逃げ道になり、通信もコストも発生しない。
> 4. Googleマップを外部リンクで開く方式では座標が返ってこないため、判定には使えない。アプリ内で座標を取得すること。
> 5. 地図に吉方位の扇形を描く場合、投影後の座標で直線的な扇形を描くこと（判定と描画を一致させる）。
> 6. **基準点の座標は端末内に保存し、サーバに送らないこと。** 位置情報の許可は必須にせず、住所検索でも設定できること。
> 7. 受け入れ基準は §7 のチェックリスト。特に東京→大阪（254.3°／西）と東京→パリ（277.4°／西）を確認すること。
>
> 着手前に、仕様書 §0 の残り3点（地図サービス／対応範囲／距離の下限）を確定して回答してください。
