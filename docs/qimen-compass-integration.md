# 奇門遁甲アプリ × ゆめコンパス 統合仕様書（Codex 引き継ぎ用）

このドキュメントは、既存の奇門遁甲アプリ（Codex で作成済み／イベント別の吉凶方位ロジックを保有）に、
方位磁石アプリ「ゆめコンパス」（`compass.html`）を統合するための仕様をまとめたものです。

- コンパス側リポジトリ: `ayukat8/-` / `compass.html`（単一HTML・外部ライブラリ非依存）
- 想定する完成形: **イベントを1タップ → コンパスが起動 → その日（またはその時辰）の吉方位が文字盤に重なって表示され、実際に方位を測れる**

---

## 0. 最初に決めてほしいこと（Codex側で確認が必要な3点）

実装前に、既存の奇門遁甲ロジックについて以下を確定してください。以降の仕様はこの3つで分岐します。

| # | 確認事項 | 選択肢 | 仕様への影響 |
|---|---|---|---|
| 1 | 方位の粒度 | 八方位（45°刻み）/ 二十四山（15°刻み） | 文字盤のセクター幅、判定の厳しさ、磁気偏角補正の要否 |
| 2 | 時間の粒度 | 日家奇門（1日単位）/ 時家奇門（2時間＝1時辰単位） | 有効期限バッジ・自動更新の要否 |
| 3 | アプリの実装形態 | 素のHTML+JS / React等のSPA / ネイティブWebView | コンパスの組み込み方（§3） |

**推奨は「八方位・時家（あれば）・同一オリジンのJSモジュール」**です。理由は各章に記載します。

## 1. ゴールとユーザー体験

### 1タップの定義

```
[イベント一覧画面]                    [コンパス画面]
 ┌──────────────┐
 │ 🎓 勉強・試験    │  ← このカードのタップ1回で
 │ 💗 恋愛・出会い   │     ・センサー利用許可
 │ 💰 お金・買い物   │     ・吉方位データの受け渡し
 │ 🧳 旅行・引っ越し │     ・コンパス起動
 └──────────────┘     をすべて完了させる
```

**重要**: iOS ではセンサー許可（`DeviceOrientationEvent.requestPermission()`）を
**ユーザーのタップハンドラ内から直接**呼ぶ必要があります。
`await fetch(...)` などを挟んでから呼ぶとユーザージェスチャの文脈が切れ、iOS の一部バージョンで拒否されます。

したがって **吉方位データの取得はタップ前に済ませておき**、タップハンドラでは同期的に許可要求を呼ぶ設計にしてください。

```js
card.addEventListener("click", () => {
  // ❌ await getAdvice() をここで挟まない
  compass.start();          // この中で requestPermission() を同期的に呼ぶ
  compass.setSectors(cachedAdvice[eventId].directions);  // データは事前取得済み
});
```

### コンパス画面でできること

1. 端末が向いている方位を、文字盤と「東南 / 132°」の表示で確認
2. 吉方位セクターが金色、凶方位セクターが灰色で文字盤に重なる
3. **吉方位を向くと**、文字盤が発光＋バイブレーション＋「生門 ◎ 東南」と表示
4. 下部のチップでイベントを切り替え（画面遷移なし・再許可なし）
5. 時家奇門の場合、「この方位はあと 47分」の残り時間バッジ

## 2. データ契約（Codex 側が実装する部分）

奇門遁甲ロジックを、次の1関数として公開してください。**これが唯一の結合点**です。

```ts
type Verdict = "auspicious" | "inauspicious" | "neutral";

interface DirectionVerdict {
  bearing: number;   // セクター中心の方位角。真北基準・時計回り・0〜359.99
                     // 例) 北=0, 東=90, 南=180, 西=270, 東南=135
  span: number;      // セクターの幅（度）。八方位=45、二十四山=15
  name: string;      // 表示名。"東南" / "巽" / "辰" など
  verdict: Verdict;
  rank?: number;     // 同じ verdict 内の優先順位。1が最良
  title?: string;    // 格・門の名称。"生門" "青龍返首" など（既存ロジックの値をそのまま）
  note?: string;     // 一言説明。30字程度
}

interface EventAdvice {
  eventId: string;    // "study" | "love" | "money" | ...
  eventName: string;  // "勉強・試験"
  icon?: string;      // 絵文字1文字
  directions: DirectionVerdict[];
  validFrom: string;  // ISO8601（例 "2026-07-25T13:00:00+09:00"）
  validTo: string;    // ISO8601。日家なら当日の終わり、時家なら2時間後
}

interface Advice {
  timezone: string;        // "Asia/Tokyo"
  basis: "day" | "hour";   // 日家 / 時家
  events: EventAdvice[];
  origin?: {               // 方位の基準点（§5参照）。未設定なら現在地とみなす
    label: string;         // "自宅"
    lat: number;
    lng: number;
  };
}

/** 指定時刻の盤を立てて、全イベントの吉凶方位を返す */
export function getAdvice(at: Date): Advice;
```

### 契約上の約束事

- `bearing` は**必ず真北基準**にしてください（磁北ではありません）。磁気偏角の吸収はコンパス側の責務です。
- 中宮（方位なし）は `directions` に含めないでください。表示不能です。代わりに `EventAdvice.note` などで「今回は中宮のため方位取り不可」と伝えてください。
- セクターが重ならないこと。同一 `bearing` に複数の判定を返さないでください。
- 吉方位が1つも無い日もあり得ます。その場合 `directions` に凶方位だけを入れて返してください（コンパス側は「今日は吉方位がありません」と表示します）。

## 3. 組み込み方式

### 推奨: 同一オリジンのJSモジュールとして取り込む

`compass.html` から描画部分を切り出し、`compass.js` + `compass.css` として奇門遁甲アプリに同梱します。

**iframe は避けてください。** 理由:

- iOS の `requestPermission()` は原則としてトップレベル文脈が必要で、クロスオリジンのiframeからは通りません
- 同一オリジンでも `<iframe allow="gyroscope; accelerometer; magnetometer">` の付与が必須で、抜けると無言で動かなくなります
- 権限の再要求がiframe単位で発生し、「1タップ」の要件を満たせません

別ページ遷移（`compass.html?event=study`）も可能ですが、イベント切替のたびに再読み込み＝**iOSでは再度の許可ダイアログ**になるため、体験が落ちます。

### コンパス側が公開するAPI（この形に合わせて切り出します）

```js
const compass = mountCompass(containerEl, {
  sectors: [],            // DirectionVerdict[]
  declination: 0,         // 磁気偏角の補正値（度）。§4参照
  labelStyle: "kanji",    // "kanji"（北/東南）| "hakke"（坎/巽）
  onHeading(deg) {},              // 毎フレーム。現在の方位角（真北基準）
  onSectorEnter(sector) {},       // 吉凶セクターに入った瞬間
  onSectorLeave(sector) {},
  onError(code, detail) {},       // §6のエラーコード
});

compass.start();              // ← 必ずユーザー操作のハンドラ内から同期的に呼ぶ
compass.setSectors(list);     // イベント切替時。再許可は発生しない
compass.setDeclination(deg);
compass.destroy();
```

### 既存 `compass.html` に実装済みで、再実装が不要な部分

Codex 側で作り直さないでください。以下はハマりどころを潰し済みです。

| 実装済みの処理 | 内容 |
|---|---|
| iOS の方位取得 | `webkitCompassHeading`（真北基準）を優先使用 |
| Android の方位取得 | `deviceorientationabsolute` の `alpha` を反転し、`screen.orientation.angle` で画面回転を補正 |
| 0°/360°またぎ | 最短弧で補間。355°→5° で長い方に1周しない |
| 文字盤のラベル | 盤の回転を打ち消して常に読める向きを維持 |
| 16方位名の算出 | `Math.round(heading / 22.5) % 16` |
| センサー不可環境 | ドラッグで回せるデモモードに自動フォールバック |
| 権限拒否・非対応 | 日本語の案内画面と再試行導線 |

## 4. 方位の基準を揃える（最重要の技術的注意）

**奇門遁甲の方位は真北基準ですが、端末が返す値は真北とは限りません。**

| 環境 | 返す値 | 基準 |
|---|---|---|
| iOS Safari | `webkitCompassHeading` | **真北**（OS側で偏角補正済み） |
| Android Chrome | `deviceorientationabsolute` の `alpha` | **磁北**（偏角補正なし） |

日本の磁気偏角は西偏 **約7〜9°**（東京で約7.5°西偏、札幌で約9.5°、那覇で約5°）。
真北方位 = 磁北方位 − 西偏角、の関係になります。

### 方針

- **八方位（45°幅）運用なら、補正なしでも実用上ほぼ問題ありません。** セクター幅に対して誤差が十分小さいためです。
- **二十四山（15°幅）を使うなら補正必須です。** 8°の誤差はセクター幅の半分を超え、隣の山に誤判定します。
- 補正する場合の実装は2択:
  1. **固定値**: `declination: -7.5` を渡す（日本国内向け・実装が軽い・端の地域で±2°の残差）
  2. **現在地から算出**: Geolocation で緯度経度を取り、簡易の偏角テーブルを引く（精度は上がるが位置情報の許可が追加で必要）

**推奨**: まず八方位＋補正なしで出す。二十四山に進む段階で固定値補正を入れる。

### 精度の伝え方

スマホの磁気センサーは、金属机・スマホケースのマグネット・電車内などで簡単に10°以上ずれます。
断定的な表示は避け、**セクター境界から±5°以内では「境界付近です」と表示**し、
「8の字に動かすと精度が上がります」の案内（実装済み）を残してください。

## 5. 「どこで測るか」の問題（仕様として要確認）

奇門遁甲の方位取りは通常、**基準点（自宅など）から目的地を見た方角**で判断します。
一方コンパスが測れるのは「**いま端末がどちらを向いているか**」だけです。この2つは別物です。

対応方針は2案。Codex側の既存仕様に合わせて選んでください。

- **案A（軽い・推奨）**: 「基準点に立って測ってください」とコンパス画面に一文添えるだけ。実装追加なし。
- **案B（本格）**: `Advice.origin` に基準点（自宅）を持たせ、Geolocation で現在地を取得。
  現在地が基準点から離れている場合は「基準点から○○km離れています」と警告を出す。
  さらに目的地を指定できるなら、基準点→目的地の方位角を計算して「目的地は東南（132°）＝吉方位です」と判定できます。

方位角の計算式（球面／十分な精度）:

```js
function bearing(lat1, lng1, lat2, lng2) {
  const toRad = d => d * Math.PI / 180;
  const φ1 = toRad(lat1), φ2 = toRad(lat2), Δλ = toRad(lng2 - lng1);
  const y = Math.sin(Δλ) * Math.cos(φ2);
  const x = Math.cos(φ1) * Math.sin(φ2) - Math.sin(φ1) * Math.cos(φ2) * Math.cos(Δλ);
  return (Math.atan2(y, x) * 180 / Math.PI + 360) % 360;  // 真北基準
}
```

## 6. エラーと制約

| コード | 発生条件 | 画面の出し方 |
|---|---|---|
| `insecure-context` | http や `file://` で開いた | 「httpsのページとして開いてね」＋デモモード導線 |
| `unsupported` | センサー非搭載（主にPC） | デモモード（ドラッグで回せる）に誘導 |
| `permission-denied` | iOS で許可を拒否 | 再試行ボタン＋「設定→Safari→モーションと画面の向きのアクセス」の案内 |
| `no-reading` | 許可は下りたが2.5秒間データが来ない | アプリ内ブラウザの可能性。「Safari/Chromeで開く」を案内 |

**追加の既知制約**:

- **https 必須**（secure context）。ローカル確認は `localhost` なら可。
- **LINE・Instagram等のアプリ内ブラウザではセンサーが取れないことがあります。** 外部ブラウザで開く導線を用意してください。
- iOS では**ページを読み込むたびに許可ダイアログ**が出ます。SPA内で画面遷移する設計（§3）にすれば1セッション1回で済みます。

## 7. 画面仕様

### コンパス画面の構成（上から）

1. イベント名 + アイコン（例: 🎓 勉強・試験）
2. 時家の場合、有効期限バッジ「〜15:00 まで（あと47分）」
3. 文字盤（既存デザイン: パステルピンク／明朝体）
   - 吉方位セクター: 金色 `#dbb26a` の扇形、`opacity: 0.35`、外周にセクター名と `title`
   - 凶方位セクター: 灰色 `#b9adb3` の扇形、`opacity: 0.2`
   - 上部の▼が現在向いている方位
4. 大きな方位表示「東南 / 132°」
5. 判定行: 吉方位を向いていれば「◎ 生門 — 学びに追い風」、凶なら「△ この方角は今日は避けて」
6. イベント切替チップ（横スクロール）

### フィードバック

- 吉セクターに入った瞬間: 文字盤の縁が金色に光る（0.4秒）＋ `navigator.vibrate(40)`
- 同じセクター内での再発火は抑制（`onSectorEnter` は入った瞬間のみ）
- `prefers-reduced-motion` が有効なら発光アニメーションを無効化（実装済み）

### デザイン方針

既存の「ゆめコンパス」の世界観（ミルキーピンク＋ラベンダー、明朝体、余白多め）を維持してください。
奇門遁甲側のUIがこれと大きく違う場合は、**コンパス画面だけこの世界観**にして構いません。
吉方位の金色は、この配色の中で唯一の強い色として機能します。

## 8. 受け入れ基準（実機テスト項目）

- [ ] iOS Safari 実機で、イベントカードのタップ**1回**で許可ダイアログ→コンパス起動まで到達する
- [ ] Android Chrome 実機で、北を向いたとき表示が 0°±10° に収まる
- [ ] 端末を横持ちにしても方位が90°ずれない（`screen.orientation.angle` 補正の確認）
- [ ] 北のあたりで左右に振っても、文字盤が長い方に1周しない
- [ ] イベントチップを切り替えたとき、**許可ダイアログが再表示されない**
- [ ] 吉方位を向いたとき、発光とバイブが1回だけ発火する
- [ ] PCで開いたときデモモードに落ち、ドラッグで回せる
- [ ] 吉方位が0件の日でも画面が壊れない
- [ ] 時家の場合、時辰をまたいだ時点で盤が自動更新される
- [ ] 機内モード（位置情報なし）でも、コンパス自体は動く

## 10. 表示上の注意

占いコンテンツのため、方位の判定は**参考情報**として表示してください。
また、コンパスの精度は端末の磁気センサーに依存し、周囲の金属や磁石の影響を受けます。
「歩きスマホをしない」旨の注意を、コンパス画面のどこかに小さく入れておくと安全です。
