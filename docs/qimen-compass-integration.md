# 奇門遁甲アプリ × ゆめコンパス 統合仕様書（Codex 引き継ぎ用）

このドキュメントは、既存の奇門遁甲アプリ（Codex で作成済み／イベント別の吉凶方位ロジックを保有）に、
方位磁石アプリ「ゆめコンパス」（`compass.html`）を統合するための仕様をまとめたものです。

- コンパス側リポジトリ: `ayukat8/-` / `compass.html`（単一HTML・外部ライブラリ非依存）
- 関連仕様: [`destination-bearing-maps.md`](./destination-bearing-maps.md)（地図連携による目的地の方位判定）
- 想定する完成形: **イベントを1タップ → コンパスが起動 → その日（またはその時辰）の吉方位が文字盤に重なって表示され、実際に方位を測れる**
- **コンパスが使えない端末・環境では、従来の奇門遁甲盤の表示に自動で切り替わり、同じ吉凶情報を読める**

---

## 0. 最初に決めてほしいこと（Codex側で確認が必要な4点）

実装前に、既存の奇門遁甲アプリについて以下を確定してください。以降の仕様はこの4つで分岐します。

| # | 確認事項 | 選択肢 | 仕様への影響 |
|---|---|---|---|
| 1 | 方位の粒度 | 八方位（45°刻み）/ 二十四山（15°刻み） | 文字盤のセクター幅、判定の厳しさ、磁気偏角補正の要否（§5） |
| 2 | 時間の粒度 | 日家奇門（1日単位）/ 時家奇門（2時間＝1時辰単位） | 有効期限バッジ・自動更新の要否 |
| 3 | アプリの実装形態 | 素のHTML+JS / React等のSPA / ネイティブWebView | コンパスの組み込み方（§4） |
| 4 | **既存の盤の向き** | 上が南（伝統的な上南下北）/ 上が北 | 盤モードとコンパスモードで上下が逆になるため、表示ラベルの要否（§2・§8） |

**推奨は「八方位・時家（あれば）・同一オリジンのJSモジュール」**です。理由は各章に記載します。

## 1. ゴールとユーザー体験

### 1タップの定義

```
[イベント一覧画面]                    [コンパス画面]
 ┌──────────────┐
 │ 🎓 勉強・試験    │  ← このカードのタップ1回で
 │ 💗 恋愛・出会い   │     ・センサー利用許可
 │ 💰 お金・買い物   │     ・吉方位データの受け渡し
 │ 🧳 旅行・引っ越し │     ・コンパス起動
 └──────────────┘     をすべて完了させる
```

**重要**: iOS ではセンサー許可（`DeviceOrientationEvent.requestPermission()`）を
**ユーザーのタップハンドラ内から直接**呼ぶ必要があります。
`await fetch(...)` などを挟んでから呼ぶとユーザージェスチャの文脈が切れ、iOS の一部バージョンで拒否されます。

したがって **吉方位データの取得はタップ前に済ませておき**、タップハンドラでは同期的に許可要求を呼ぶ設計にしてください。

```js
card.addEventListener("click", () => {
  // ❌ await getAdvice() をここで挟まない
  compass.start();          // この中で requestPermission() を同期的に呼ぶ
  compass.setSectors(cachedAdvice[eventId].directions);  // データは事前取得済み
});
```

### コンパスモードでできること

1. 端末が向いている方位を、文字盤と「東南 / 132°」の表示で確認
2. 吉方位セクターが金色、凶方位セクターが灰色で文字盤に重なる
3. **吉方位を向くと**、文字盤が発光＋バイブレーション＋「生門 ◎ 東南」と表示
4. 下部のチップでイベントを切り替え（画面遷移なし・再許可なし）
5. 時家奇門の場合、「この方位はあと 47分」の残り時間バッジ

## 2. 動作モード（コンパスモード / 盤モード）

### 大原則

**両モードは同じ `Advice`（§3）から描画します。** 表示形式が違うだけで、判定内容は完全に一致させてください。
ロジックを二重に持つと必ず食い違います。データ取得→判定はモードに依存しない層に置いてください。

```
        getAdvice(now)  ←  奇門遁甲ロジック（1つだけ）
              │
      ┌───────┴───────┐
      ▼               ▼
 コンパスモード      盤モード
（方位を測れる）   （方位は自分で把握）
```

### モード決定フロー

```
起動
 │
 ├─ isSecureContext === false ────────────────→ 盤モード（コンパス不可を表示）
 │
 ├─ 保存された設定が "board" ──────────────────→ 盤モード
 │
 └─ それ以外 → コンパスモードを試行
                │
                ├─ 2.5秒以内に方位を取得 ──────→ コンパスモード（成功）
                │
                └─ 拒否 / 非対応 / 無反応 ─────→ 盤モードへ自動フォールバック
                                                （細いバーで理由を一言だけ表示）
```

**コンパスが使えないことをエラー画面で伝えて止めないでください。** 黙って盤モードに落とし、
画面上部に「コンパスが使えないため、盤で表示しています」と一行だけ添えるのが正解です。
奇門遁甲アプリとして本来の機能は何も失われていないためです。

### モードの往復

- 盤モードの上部に常に「**コンパスで測る**」ボタンを置き、いつでも再挑戦できるようにする
- コンパスモードにも「**盤で見る**」ボタンを置く（コンパスが不正確なとき・室内で落ち着いて確認したいとき用）
- ユーザーが手動で選んだモードは `localStorage` に保存し、次回起動時に引き継ぐ
- 自動フォールバックで盤モードになった場合は**保存しない**（環境が変われば次回コンパスが使える可能性があるため）
- モードを切り替えても、**選択中のイベントと表示日時は維持**すること

### デモモード（ドラッグで回せる）の扱い ※重要

現在の `compass.html` には、センサーが無い環境でドラッグして文字盤を回せるデモモードがあります。
**統合後、これを一般ユーザーに出さないでください。**

デモモードは方位を測っていないため、これで吉凶を判断させると**誤った方角を吉方位だと表示することになります**。
センサーが使えないユーザーの正しい行き先は盤モードです。
デモモードは開発・デザイン確認用として `?demo=1` のようなフラグの下に隔離してください。

## 3. データ契約（Codex 側が実装する部分）

奇門遁甲ロジックを、次の1関数として公開してください。**これが唯一の結合点**です。

```ts
type Verdict = "auspicious" | "inauspicious" | "neutral";

interface DirectionVerdict {
  bearing: number;   // セクター中心の方位角。真北基準・時計回り・0〜359.99
                     // 例) 北=0, 東=90, 南=180, 西=270, 東南=135
  span: number;      // セクターの幅（度）。八方位=45、二十四山=15
  name: string;      // 表示名。"東南" / "巽" / "辰" など
  verdict: Verdict;
  palace?: number;   // 九宮の番号 1〜9（§8の対応表）。既存ロジックが持っていれば渡す
  rank?: number;     // 同じ verdict 内の優先順位。1が最良
  title?: string;    // 格・門の名称。"生門" "青龍返首" など（既存ロジックの値をそのまま）
  note?: string;     // 一言説明。30字程度
}

interface EventAdvice {
  eventId: string;    // "study" | "love" | "money" | ...
  eventName: string;  // "勉強・試験"
  icon?: string;      // 絵文字1文字
  directions: DirectionVerdict[];
  validFrom: string;  // ISO8601（例 "2026-07-25T13:00:00+09:00"）
  validTo: string;    // ISO8601。日家なら当日の終わり、時家なら2時間後
}

interface Advice {
  timezone: string;        // "Asia/Tokyo"
  basis: "day" | "hour";   // 日家 / 時家
  events: EventAdvice[];
  centerNote?: string;     // 中宮に関する注記など、方位に落とせない情報
  origin?: {               // 方位の基準点（§6参照）。未設定なら現在地とみなす
    label: string;         // "自宅"
    lat: number;
    lng: number;
  };
}

/** 指定時刻の盤を立てて、全イベントの吉凶方位を返す */
export function getAdvice(at: Date): Advice;
```

### 契約上の約束事

- `bearing` は**必ず真北基準**にしてください（磁北ではありません）。磁気偏角の吸収はコンパス側の責務です。
- 中宮（方位なし）は `directions` に含めないでください。方位として表示できません。
  伝えたい内容は `centerNote` に入れてください（盤モードでは中央のマスに表示できます）。
- セクターが重ならないこと。同一 `bearing` に複数の判定を返さないでください。
- 吉方位が1つも無い日もあり得ます。その場合 `directions` に凶方位だけを入れて返してください
  （両モードとも「今日は吉方位がありません」と表示します）。

## 4. 組み込み方式

### 推奨: 同一オリジンのJSモジュールとして取り込む

`compass.html` から描画部分を切り出し、`compass.js` + `compass.css` として奇門遁甲アプリに同梱します。

**iframe は避けてください。** 理由:

- iOS の `requestPermission()` は原則としてトップレベル文脈が必要で、クロスオリジンのiframeからは通りません
- 同一オリジンでも `<iframe allow="gyroscope; accelerometer; magnetometer">` の付与が必須で、抜けると無言で動かなくなります
- 権限の再要求がiframe単位で発生し、「1タップ」の要件を満たせません

別ページ遷移（`compass.html?event=study`）も可能ですが、イベント切替のたびに再読み込み＝**iOSでは再度の許可ダイアログ**になるため、体験が落ちます。

### コンパス側が公開するAPI（この形に合わせて切り出します）

```js
const compass = mountCompass(containerEl, {
  sectors: [],            // DirectionVerdict[]
  declination: 0,         // 磁気偏角の補正値（度）。§5参照
  labelStyle: "kanji",    // "kanji"（北/東南）| "hakke"（坎/巽）
  onHeading(deg) {},              // 毎フレーム。現在の方位角（真北基準）
  onSectorEnter(sector) {},       // 吉凶セクターに入った瞬間
  onSectorLeave(sector) {},
  onUnavailable(code, detail) {}, // §7。この中で盤モードに切り替える
});

compass.start();              // ← 必ずユーザー操作のハンドラ内から同期的に呼ぶ
compass.setSectors(list);     // イベント切替時。再許可は発生しない
compass.setDeclination(deg);
compass.destroy();            // 盤モードに切り替えるときに呼ぶ（センサー購読を解除）
```

`onUnavailable` は「起動できなかった」「途中で読めなくなった」の両方で呼ばれます。
呼ばれたら盤モードへ切り替えてください。

### 既存 `compass.html` に実装済みで、再実装が不要な部分

Codex 側で作り直さないでください。以下はハマりどころを潰し済みです。

| 実装済みの処理 | 内容 |
|---|---|
| iOS の方位取得 | `webkitCompassHeading`（真北基準）を優先使用 |
| Android の方位取得 | `deviceorientationabsolute` の `alpha` を反転し、`screen.orientation.angle` で画面回転を補正 |
| 0°/360°またぎ | 最短弧で補間。355°→5° で長い方に1周しない |
| 文字盤のラベル | 盤の回転を打ち消して常に読める向きを維持 |
| 16方位名の算出 | `Math.round(heading / 22.5) % 16` |
| 権限拒否・非対応の検出 | 2.5秒のタイムアウト付きで判定（→ 盤モードへの切替に使う） |

## 5. 方位の基準を揃える（最重要の技術的注意）

**奇門遁甲の方位は真北基準ですが、端末が返す値は真北とは限りません。**

| 環境 | 返す値 | 基準 |
|---|---|---|
| iOS Safari | `webkitCompassHeading` | **真北**（OS側で偏角補正済み） |
| Android Chrome | `deviceorientationabsolute` の `alpha` | **磁北**（偏角補正なし） |

日本の磁気偏角は西偏 **約7〜9°**（東京で約7.5°西偏、札幌で約9.5°、那覇で約5°）。
真北方位 = 磁北方位 − 西偏角、の関係になります。

### 方針

- **八方位（45°幅）運用なら、補正なしでも実用上ほぼ問題ありません。** セクター幅に対して誤差が十分小さいためです。
- **二十四山（15°幅）を使うなら補正必須です。** 8°の誤差はセクター幅の半分を超え、隣の山に誤判定します。
- 補正する場合の実装は2択:
  1. **固定値**: `declination: -7.5` を渡す（日本国内向け・実装が軽い・端の地域で±2°の残差）
  2. **現在地から算出**: Geolocation で緯度経度を取り、簡易の偏角テーブルを引く（精度は上がるが位置情報の許可が追加で必要）

**推奨**: まず八方位＋補正なしで出す。二十四山に進む段階で固定値補正を入れる。

### 精度の伝え方

スマホの磁気センサーは、金属机・スマホケースのマグネット・電車内などで簡単に10°以上ずれます。
断定的な表示は避け、**セクター境界から±5°以内では「境界付近です」と表示**し、
「8の字に動かすと精度が上がります」の案内（実装済み）を残してください。

## 6. 「どこで測るか」の問題（仕様として要確認）

奇門遁甲の方位取りは通常、**基準点（自宅など）から目的地を見た方角**で判断します。
一方コンパスが測れるのは「**いま端末がどちらを向いているか**」だけです。この2つは別物です。

対応方針は2案。Codex側の既存仕様に合わせて選んでください。

- **案A（軽い）**: 「基準点に立って測ってください」とコンパス画面に一文添えるだけ。実装追加なし。
- **案B（本格）**: 基準点（自宅）を保存し、地図から目的地を指定して、基準点→目的地の方位角を計算して判定する。
  → **仕様は別紙 [`destination-bearing-maps.md`](./destination-bearing-maps.md) にまとめてあります。**

**案Bは盤モードでも有効です。** コンパスが無くても、目的地さえ指定できれば方位角は計算でき、吉凶を判定できます。
つまり案Bは、**コンパスを起動できないユーザーにとって最も確実な方位取りの手段**になります。
§2のフォールバック方針と組み合わせると、盤モードの価値が大きく上がります。

なお、地図から得られる方位角は**常に真北基準**なので、§5の磁北問題は案Bには一切影響しません。

## 7. コンパスが使えないケースと、その扱い

すべて**エラー画面ではなく盤モードへのフォールバック**として扱ってください。

| コード | 発生条件 | 盤モード上部に出す一言 |
|---|---|---|
| `insecure-context` | http や `file://` で開いた | 「この環境ではコンパスが使えません」 |
| `unsupported` | センサー非搭載（主にPC） | 「この端末にはコンパスがありません」 |
| `permission-denied` | iOS で許可を拒否 | 「コンパスの利用が許可されていません」＋許可方法の説明リンク |
| `no-reading` | 許可は下りたが2.5秒間データが来ない | 「コンパスの反応がありません」＋「Safari/Chromeで開く」案内 |
| `lost` | 測定中にデータが途切れた（10秒） | 「コンパスの反応が止まりました」 |

### 補足しておくべき既知の制約

- **https 必須**（secure context）。ローカル確認は `localhost` なら可。
- **LINE・Instagram等のアプリ内ブラウザではセンサーが取れないことがあります。** かなり多いケースなので、
  `no-reading` の案内には「外部ブラウザで開く」導線を必ず入れてください。
- iOS では**ページを読み込むたびに許可ダイアログ**が出ます。SPA内で画面遷移する設計（§4）にすれば1セッション1回で済みます。
- PC利用者は常に盤モードになります。**PCでの表示崩れを盤モード側で必ず確認してください。**

## 8. 画面仕様

### 8-1. コンパスモード（上から）

1. イベント名 + アイコン（例: 🎓 勉強・試験）
2. 時家の場合、有効期限バッジ「〜15:00 まで（あと47分）」
3. 文字盤（既存デザイン: パステルピンク／明朝体、**上が北で固定**）
   - 吉方位セクター: 金色 `#dbb26a` の扇形、`opacity: 0.35`、外周にセクター名と `title`
   - 凶方位セクター: 灰色 `#b9adb3` の扇形、`opacity: 0.2`
   - 上部の▼が現在向いている方位
4. 大きな方位表示「東南 / 132°」
5. 判定行: 吉方位を向いていれば「◎ 生門 — 学びに追い風」、凶なら「△ この方角は今日は避けて」
6. イベント切替チップ（横スクロール）
7. 「盤で見る」への導線

**フィードバック**

- 吉セクターに入った瞬間: 文字盤の縁が金色に光る（0.4秒）＋ `navigator.vibrate(40)`
- 同じセクター内での再発火は抑制（`onSectorEnter` は入った瞬間のみ）
- `prefers-reduced-motion` が有効なら発光アニメーションを無効化（実装済み）

### 8-2. 盤モード

既存の奇門遁甲盤の表示をそのまま活かしつつ、**吉凶が一目で分かる着色**と**方角の見つけ方**を足します。

1. 上部の細いバー: フォールバックした理由（§7）＋「コンパスで測る」ボタン
2. イベント名 + 有効期限バッジ（コンパスモードと共通）
3. **九宮盤**（3×3）— 各マスに `name` / `title` を表示し、`verdict` で着色
   - 吉: 金色の枠と淡い金の地、右上に ◎
   - 凶: 灰色の地、右上に △
   - 中央のマスには `centerNote` を表示
   - **盤の上が南か北かを必ずラベルで明示**（§0-4）。伝統的な盤は上が南、コンパスは上が北で逆になります。
     見比べる人が混乱するため、「北を上にする」トグルを付けると親切です。
4. **吉方位の一覧**（盤が読めない人向け）— 「◎ 東南（132°）生門 — 学びに追い風」の行を、`rank` 順に並べる
5. **「方角の見つけ方」**（折りたたみ）— コンパスが無い人がその場で方角を知るための手当:
   - 地図アプリを開く（地図は上が北）
   - 太陽の位置からの概算（日本・晴天時、±15°程度）:

     | 時刻 | 太陽のある方角 |
     |---|---|
     | 6時ごろ | 東 |
     | 9時ごろ | 南東 |
     | 12時ごろ | 南 |
     | 15時ごろ | 南西 |
     | 18時ごろ | 西 |

   - 前にコンパスで測ったときの目印を思い出す（「ベランダが南東」など）
6. イベント切替チップ（コンパスモードと共通コンポーネント）

| 270 | 西 | 兌 | 7 |
| 315 | 北西 | 乾 | 6 |
| （方位なし） | 中央 | — | 5 |

### 8-4. デザイン方針

既存の「ゆめコンパス」の世界観（ミルキーピンク＋ラベンダー、明朝体、余白多め）を維持してください。
奇門遁甲側のUIがこれと大きく違う場合は、**コンパス画面だけこの世界観**にして構いませんが、
盤モードとコンパスモードを行き来する以上、**イベント名・バッジ・チップは共通コンポーネント**にして
見た目を揃えてください。ここが揃っていないと、モード切替が「別アプリに飛んだ」ように感じられます。

吉方位の金色は、この配色の中で唯一の強い色として機能します。両モードで同じ金色を使ってください。

## 9. 受け入れ基準（実機テスト項目）

### コンパスモード

- [ ] iOS Safari 実機で、イベントカードのタップ**1回**で許可ダイアログ→コンパス起動まで到達する
- [ ] Android Chrome 実機で、北を向いたとき表示が 0°±10° に収まる
- [ ] 端末を横持ちにしても方位が90°ずれない（`screen.orientation.angle` 補正の確認）
- [ ] 北のあたりで左右に振っても、文字盤が長い方に1周しない
- [ ] イベントチップを切り替えたとき、**許可ダイアログが再表示されない**
- [ ] 吉方位を向いたとき、発光とバイブが1回だけ発火する

### フォールバックと盤モード

- [ ] PCで開いたとき、**エラー画面で止まらず**盤モードで吉凶が読める
- [ ] iOSで許可を「許可しない」にしても盤モードに落ちる
- [ ] アプリ内ブラウザ（LINE等）で開いても盤モードに落ち、外部ブラウザへの導線が出る
- [ ] 盤モードの「コンパスで測る」から、再度コンパスに移行できる
- [ ] 手動で盤モードを選ぶと、次回起動時も盤モードで開く
- [ ] 自動フォールバックで盤モードになった場合は、次回もコンパスを試行する
- [ ] モードを切り替えても、選択中のイベントと日時が維持される
- [ ] **両モードで、同じ日・同じイベントの吉凶表示が完全に一致する**
- [ ] 盤の上が南か北かがラベルで明示されている
- [ ] デモモード（ドラッグ）が一般ユーザーに露出していない
- [ ] 吉方位が0件の日でも、両モードとも画面が壊れない
- [ ] 時家の場合、時辰をまたいだ時点で両モードとも盤が自動更新される
- [ ] 機内モード（位置情報なし）でも、両モードとも動く

## 11. 表示上の注意

占いコンテンツのため、方位の判定は**参考情報**として表示してください。
また、コンパスの精度は端末の磁気センサーに依存し、周囲の金属や磁石の影響を受けます。
「歩きスマホをしない」旨の注意を、コンパス画面のどこかに小さく入れておくと安全です。

## 付録: Codex にそのまま渡す指示文

> 既存の奇門遁甲アプリに、別途作成済みの方位磁石コンポーネント「ゆめコンパス」を統合してください。
> 仕様は `docs/qimen-compass-integration.md` の通りです。要点は以下:
>
> 1. **基本はコンパスモード**。イベントカードのタップ1回で、センサー許可・データ受け渡し・コンパス起動まで
>    完了させること。iOS の制約上、`DeviceOrientationEvent.requestPermission()` はタップハンドラ内から
>    同期的に呼ぶこと。吉方位データはタップ前に取得しておくこと。
> 2. **コンパスが使えない場合は、エラー画面で止めず、従来の奇門遁甲盤の表示（盤モード）に自動で切り替える**こと。
>    PC・許可拒否・アプリ内ブラウザ・非https のすべてが対象。理由は上部に一行だけ添える。
>    両モードは往復でき、手動で選んだモードは記憶する。
> 3. 両モードは**同一の `getAdvice(at: Date): Advice` から描画**し、判定ロジックを二重に持たないこと。
>    型定義は仕様書の §3 を参照。`bearing` は真北基準・時計回りで返すこと。
> 4. 現在コンパスに実装されているデモモード（ドラッグで文字盤を回せる機能）は、
>    **一般ユーザーに露出させないこと**。方位を測っていないため、吉凶判断に使うと誤情報になる。
>    正しいフォールバック先は盤モード。
> 5. コンパスは iframe ではなく同一オリジンのJSモジュールとして組み込むこと（理由は §4）。
> 6. 文字盤に吉方位セクターを金色、凶方位を灰色で重ね、向いた瞬間に発光とバイブでフィードバックすること。
>    盤モードでも同じ金色・同じ判定で着色し、吉方位の一覧と「方角の見つけ方」を添えること。
> 7. 受け入れ基準は §9 のチェックリスト。実機（iOS Safari / Android Chrome）とPCの両方で確認すること。
>
> 着手前に、仕様書 §0 の4点（方位の粒度／時間の粒度／アプリの実装形態／既存の盤の向き）を確定して回答してください。
